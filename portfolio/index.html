01

Apresentação

Estou em transição de carreira de Social Media e Operações Digitais para Quality Assurance. Na operação de conteúdo para marcas, minha rotina inclui abrir briefings, acompanhar cada demanda até a entrega, controlar prazos, revisar peças antes da publicação e montar relatórios de performance.

Nesse trabalho eu já lidava com critérios de aceite, checagem antes de liberar uma entrega, registro de problemas e leitura de indicadores. Este projeto é a primeira vez que aplico esses hábitos a software: planejei, automatizei, executei e documentei testes de uma API REST, separando com cuidado o que é defeito, o que é limitação conhecida e o que ainda depende de definição.

Este é um projeto de estudos. Ainda não tenho experiência profissional em QA.

02

Visão geral do projeto

Sistema
JSONPlaceholder, API REST pública e gratuita de demonstração (jsonplaceholder.typicode.com)
Objetivo
Validar status HTTP, contrato JSON, tratamento de erros e consistência entre requisições
Escopo
/users, /posts, /posts/{id}/comments · GET, POST, PUT, PATCH, DELETE
Ferramentas
Postman (web), Collection Runner, JavaScript (pm.test e Chai)
Ambiente
JSONPlaceholder | QA · variáveis baseUrl e maxResponseTime = 3000
Fora do escopo
Carga e desempenho, segurança aprofundada, autenticação (a API não tem)
Limitações conhecidas. A própria documentação do JSONPlaceholder informa que criação, alteração e exclusão são simuladas: nada é gravado. A API também não valida o corpo das requisições. Essas limitações foram comprovadas por testes (CT-010, CT-012, CT-014) e não são apresentadas como defeitos.
03

Estratégia de testes

Os cenários foram escolhidos depois de uma exploração inicial da API. Cada método HTTP tem pelo menos um caminho feliz e um caminho de erro, e os limites cobrem identificadores, tamanho de campo e parâmetros inesperados.

Positivos

Consulta, criação, substituição, atualização parcial e exclusão válidas.

CT-001 · 009 · 015 · 016 · 018 · 021

Negativos

Id inexistente ou inválido, corpo vazio ou malformado, método não suportado.

CT-002 · 003 · 007 · 010 · 011 · 017 · 019 · 020

Limite

Id 0 (abaixo do intervalo 1–10), parâmetro desconhecido, campos vazios, título com 5.000 caracteres.

CT-004 · 005 · 012 · 013

Integração

O dado devolvido por uma requisição vira a entrada da próxima: userId → posts → comentários; post criado → consulta.

CT-006 · 008 · 014

Critério de aprovação. Um caso é aprovado quando todas as suas verificações passam. Um 404 em cenário negativo é sucesso, e não falha.

Requisito para erros. Como a API não documenta um contrato de erros, os cenários negativos usam a semântica HTTP da RFC 9110: erro causado pelo cliente → 4xx; nenhuma resposta pode expor detalhes internos do servidor.

Verificação em todas as requisições. Um script no nível da collection confere, em cada resposta, se o tempo ficou abaixo de maxResponseTime.

05

Automação com Postman

Os testes ficam em Scripts › Post-response e rodam assim que a resposta chega. Cada pm.test é uma verificação com nome próprio, que aparece como PASS ou FAIL no Runner. Todos os scripts têm comentários em português.

Collection Script que roda em todas as 21 requisições: limite de tempo de resposta
// ===== Verificação comum a TODAS as requisições da collection =====
// Este script roda depois de cada resposta (nível da collection).
// Ele garante que nenhuma requisição demore mais que o limite definido no ambiente.
const limite = Number(pm.environment.get("maxResponseTime") || 3000);

pm.test("[Geral] Tempo de resposta abaixo de " + limite + " ms", function () {
    // pm.response.responseTime = tempo (ms) que a API levou para responder
    pm.expect(pm.response.responseTime).to.be.below(limite);
});
CT-001 Valida status, formato JSON, campos obrigatórios, tipos, valor do id e formato do e-mail. Ao final, salva o userId para outro teste.
Post-response
// CT-001 - Cenário positivo: o usuário de id 1 existe na base de demonstração
pm.test("Status HTTP deve ser 200 OK", function () {
    pm.response.to.have.status(200);
});

pm.test("Resposta deve ser um JSON válido", function () {
    pm.response.to.be.json;
});

// Guardamos o corpo da resposta em uma variável para reutilizar nas verificações
const usuario = pm.response.json();

pm.test("Campos obrigatórios presentes (id, name, username, email, address, company)", function () {
    pm.expect(usuario).to.include.all.keys("id", "name", "username", "email", "address", "company");
});

pm.test("Tipos de dados corretos", function () {
    pm.expect(usuario.id).to.be.a("number");
    pm.expect(usuario.name).to.be.a("string");
    pm.expect(usuario.email).to.be.a("string");
    pm.expect(usuario.address).to.be.an("object");
});

pm.test("O id retornado é o mesmo que foi solicitado (1)", function () {
    pm.expect(usuario.id).to.eql(1);
});

pm.test("E-mail tem formato válido", function () {
    // Expressão regular simples: texto@texto.texto
    pm.expect(usuario.email).to.match(/^[^\s@]+@[^\s@]+\.[^\s@]+$/);
});

// Integração: salvamos o id para usar no CT-006 (filtro de posts por usuário)
pm.collectionVariables.set("userId", usuario.id);
CT-006 Teste de integração: lê a variável criada pelo CT-001 e confere se o filtro devolve somente posts daquele usuário.
Post-response
// CT-006 - Integração entre requisições: usamos o userId salvo pelo CT-001.
const userIdEsperado = Number(pm.collectionVariables.get("userId"));

pm.test("Pré-condição: userId foi definido pelo CT-001", function () {
    pm.expect(userIdEsperado).to.be.above(0);
});

pm.test("Status HTTP deve ser 200 OK", function () {
    pm.response.to.have.status(200);
});

const posts = pm.response.json();

pm.test("Filtro retorna pelo menos 1 post", function () {
    pm.expect(posts.length).to.be.above(0);
});

pm.test("Consistência: TODOS os posts pertencem ao usuário filtrado", function () {
    // .every() verifica se a condição é verdadeira para cada item da lista
    const todosDoUsuario = posts.every(p => p.userId === userIdEsperado);
    pm.expect(todosDoUsuario).to.be.true;
});

// Guardamos o id do primeiro post para usar no CT-008
pm.collectionVariables.set("postId", posts[0].id);
CT-011 Teste negativo: define o requisito (4xx e nenhum detalhe interno exposto). Foi este teste que encontrou o BUG-001.
Post-response
// CT-011 - Dados inválidos: o corpo enviado NÃO é um JSON válido (está incompleto).
// Requisito de teste (boa prática HTTP - RFC 9110): erro causado pelo cliente
// deve retornar 4xx (normalmente 400 Bad Request), nunca 5xx.
pm.test("Status HTTP deve ser 400 Bad Request", function () {
    pm.response.to.have.status(400);
});

pm.test("Resposta NÃO deve expor detalhes internos do servidor (stack trace)", function () {
    pm.expect(pm.response.text()).to.not.include("at JSON.parse");
});
CT-013 Teste de limite: um script Pre-request gera 5.000 caracteres antes do envio, e o Post-response confere que nada foi truncado.
Pre-request
// Pre-request: gera um título com 5.000 letras 'A' antes de enviar
pm.collectionVariables.set("tituloGrande", "A".repeat(5000));
Post-response
// CT-013 - Teste de limite: valor muito grande em um campo de texto
pm.test("Status HTTP deve ser 201 Created", function () {
    pm.response.to.have.status(201);
});

pm.test("Título devolvido mantém os 5.000 caracteres (sem truncamento)", function () {
    pm.expect(pm.response.json().title).to.have.lengthOf(5000);

pm.response.to.have.status(n) confere o código HTTP

pm.expect(obj).to.include.all.keys(...) confere se os campos obrigatórios existem

pm.expect(v).to.be.a("number") confere o tipo do dado

.to.be.oneOf([404, 405]) aceita mais de um resultado válido

pm.collectionVariables.set(...) guarda um dado para a próxima requisição

pm.response.responseTime é o tempo de resposta, em ms

07

Bugs e melhorias

BUG-001 · defeito confirmado · severidade média

POST com JSON malformado retorna 500 e expõe o stack trace

Passos
POST /posts com o corpo { "title": "JSON sem fechamento", "userId": 1
Esperado
400 Bad Request, sem detalhes internos
Obtido
500 · SyntaxError … at JSON.parse … /app/node_modules/body-parser/lib/types/json.js
Investigação
Reproduzido no Runner e em execução individual. O script foi revisado e não tem erro (CT-011, evidência 06).
BUG-002 · defeito confirmado · severidade média

PUT em post inexistente retorna 500 e expõe o stack trace

Passos
PUT /posts/9999 com title, body e userId
Esperado
404 Not Found
Obtido
500 · TypeError: Cannot read properties of undefined (reading 'id') … json-server/lib/server/router/plural.js
Investigação
GET /posts/9999 retorna 404 corretamente, então a falha está no fluxo de atualização (CT-017, evidência 07).
OBS-001 · possível defeito, não confirmado

DELETE em post inexistente retorna 200

Por que está em aberto
A RFC 9110 não fixa um código para esse caso: 404 é o mais comum, mas 200/204 também são aceitos por idempotência. A decisão depende de um requisito do produto (CT-019).
Limitação: sem persistênciaO post "criado" no CT-009 (id 101) retorna 404 no CT-014. A documentação já avisa sobre isso.
Limitação: sem validação de entradaCorpo vazio e campos vazios recebem 201 (CT-010, CT-012). Por isso, esses casos testam o comportamento documentado.
Melhoria sugeridaTratar erros de parsing e recursos inexistentes com 4xx e mensagens genéricas, sem stack trace.

O arquivo bug-reports/README.md traz o relatório completo de cada defeito e um exemplo didático, identificado como simulação.

09

Aprendizados

  • Um 4xx pode ser o resultado certo.O que define se o teste passou é o resultado esperado, e não a cor do status. CT-002, CT-003 e CT-004 passam justamente porque recebem 404.
  • Classificar antes de reportar.Defeito, limitação documentada e comportamento indefinido pedem respostas diferentes. Só 2 dos 4 comportamentos estranhos viraram bug.
  • Investigar o próprio teste primeiro.Antes de culpar a API, revisei o script e reproduzi a falha de forma isolada. Também recusei a sugestão automática do Postman de ajustar a asserção, porque isso esconderia o defeito.
  • Encadear requisições revela inconsistências.Com variáveis de collection, o resultado de um teste vira a entrada do próximo, como em um fluxo real de uso.
  • Documentação é parte do teste.Casos, evidências e relatório permitem que outra pessoa refaça tudo e chegue ao mesmo resultado.
